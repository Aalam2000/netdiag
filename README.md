# NetDiag

Мониторинг роутера и интернета с проводного сервера.
Работает бесконечно, пишет лог, одной командой строит отчёт:
сколько было сбоев, что в каждом из них можно утверждать о причине
и зависят ли сбои от числа устройств в сети.

## Что измеряется

Каждые 5 секунд:

**Роутер по локальной сети (192.168.0.1)**
  - TCP-подключение к 192.168.0.1:80 и :443 — отвечает ли и с какой задержкой;
  - DNS-запрос к 192.168.0.1:53 — работает ли DNS-прокси роутера.

**Внешние ресурсы**
  - 8.8.8.8:53, 1.1.1.1:53, 9.9.9.9:53 (по IP);
  - google.com:443, cloudflare.com:443, github.com:443 (по имени).

Раз в 60 секунд считается **число устройств в локальной сети**: на каждый
адрес 192.168.0.0/24 уходит один пустой UDP-пакет (порт 9), ядро выполняет
ARP-запрос, ответившие считаются. В число входят и сами роутеры.
Это объективная мера нагрузки, с которой отчёт сопоставляет сбои.

## Как классифицируется каждый замер

  Состояние  | Признак
  -----------|----------------------------------------------------------
  обрыв      | недоступны все внешние ресурсы
  DNS        | по IP связь есть, но DNS роутера молчит / имена не разрешаются
  частичный  | недоступны два и более внешних ресурса, но не все
  роутер молчит | интернет работает, роутер на локальные запросы не отвечает
  норма      | всё доступно

Подряд идущие отклонения склеиваются в одно событие (пауза до 30 секунд
событие не разрывает). В список попадают события от 30 секунд, более
короткие обрывы только подсчитываются.

## Что отчёт утверждает о причине обрыва

Проводной сервер видит не всё, поэтому вердиктов три:

  Что наблюдалось во время обрыва               | Вывод
  ----------------------------------------------|---------------------------
  роутер не отвечал и по локальной сети         | роутер
  роутер отвечал медленно (в 3+ раза дольше     | признак перегрузки роутера,
  обычного) или с перебоями                     | не строгое доказательство
  роутер отвечал нормально, трафик не шёл       | роутер (NAT/WAN) или
                                                | провайдер — не различить

Третий случай прежняя версия записывала на провайдера. Это неверно:
перегруженный роутер продолжает отвечать по локальной сети, но перестаёт
пропускать трафик наружу. Различить можно по журналу линии у провайдера
или по статусу WAN в интерфейсе роутера в момент сбоя.

К роутеру однозначно относятся также отказ его DNS при работающем
интернете и молчание на локальные запросы: эти проверки не выходят за
пределы локальной сети, провайдер на них не влияет.

Главный аргумент отчёта — таблица «Зависимость от числа устройств».
Провайдер не знает, сколько устройств в локальной сети. Если сбои и
задержка ответа роутера растут вместе с числом устройств, причина внутри
сети. Если не растут, отчёт так и напишет.

## Чего отчёт не показывает

  - Качество Wi-Fi по комнатам: сервер подключён проводом. Нужен такой же
    замер с устройства, подключённого по Wi-Fi (например, малина).
  - Замирания короче 5 секунд.
  - Скорость: проверяется доступность и задержка.

## Структура

    /opt/netdiag/
    ├── netdiag.py            # основной скрипт
    ├── Dockerfile            # образ python:3.12-slim
    ├── docker-compose.yml    # запуск контейнера
    ├── data/                 # создаётся автоматически
    │   ├── netdiag.jsonl     # сырой лог (по строке JSON на замер)
    │   ├── netdiag.log       # лог приложения (старт/стоп/GAP)
    │   ├── heartbeat         # метка последнего замера
    │   └── report.txt        # сгенерированный отчёт
    └── script/
        └── netdiag.sh        # управление: start/stop/report/...

## Установка (один раз)

    cd /opt/netdiag
    chmod +x script/netdiag.sh
    sudo systemctl enable docker
    docker compose up -d --build
    sudo ln -s /opt/netdiag/script/netdiag.sh /usr/local/bin/netdiag

## Обновление скрипта на сервере

    cd /opt/netdiag && git pull
    netdiag restart        # обязательно: без перезапуска контейнер
                           # продолжит видеть старый netdiag.py

Старый лог остаётся пригодным: отчёт строится и по записям прежнего
формата, только без числа устройств и без проверки DNS роутера.

## Команды

    netdiag start      # запустить мониторинг (пересобирает образ)
    netdiag stop       # построить отчёт и остановить мониторинг
    netdiag restart    # перезапустить
    netdiag status     # статус контейнера + последние строки лога
    netdiag log        # живой лог контейнера (Ctrl+C для выхода)
    netdiag raw        # последние 10 сырых замеров из JSONL
    netdiag report     # отчёт по всем данным, мониторинг не прерывается
    netdiag report --since 2026-10-12 --until 2026-10-19
                       # отчёт за период (until не включается)
    netdiag down       # удалить контейнер (данные в data/ остаются)
    netdiag clean      # удалить контейнер И папку data/

Отчёт печатается в терминал и сохраняется в ./data/report.txt.

## Проверка после запуска

Через пару минут:

    netdiag raw

  - у внешних целей и gw_80 должно быть "ok": true;
  - в записи должно появиться поле "dev" — число устройств. Если его нет,
    смотри `netdiag status`: строка "device scan sees 0 devices" означает,
    что LAN_NET в netdiag.py не совпадает с сетью сервера;
  - если gw_dns всегда "ok": false, DNS на роутере выключен — отчёт это
    заметит и проверку учитывать не будет.

## Сколько собирать

Минимум — полная учебная неделя, чтобы в данные попали и часы пик,
и ночи, и выходные. Таблица зависимости от числа устройств требует
не меньше часа наблюдений и при малой, и при большой нагрузке.

## Простой сервера

UPS нет. Если питание пропадёт, сервер выключится, а после включения
Docker поднимет контейнер сам. Пауза между замерами дольше 60 секунд
попадает в отчёт отдельным блоком «Перерывы в наблюдении» и сбоем сети
не считается.

## Настройка

В начале netdiag.py:

    GATEWAY, LAN_NET  — адрес роутера и локальная сеть
    EXTERNAL_TARGETS  — внешние цели
    INTERVAL_SEC      — период опроса (5)
    TCP_TIMEOUT       — таймаут одной проверки (2 сек)
    OUTAGE_MIN_SEC    — минимальная длительность события для списка (30)
    DEVICE_SCAN       — считать ли устройства (True)
    DEVICE_BUCKETS    — группы по числу устройств для таблицы
    WORK_HOURS        — рабочие часы; используются для сравнения, только
                        если в данных нет числа устройств

После правки — `netdiag restart`.

## Частые вопросы

Q: Почему TCP, а не ping?
A: Роутер 192.168.0.1 не отвечает на ICMP. TCP-подключение работает
   и даёт ту же задержку.

Q: Подсчёт устройств нагружает сеть?
A: Нет: 254 пустых пакета раз в минуту.

Q: Устройств в отчёте меньше, чем ожидалось.
A: Считаются только устройства в сети LAN_NET, видимые серверу. Если
   дополнительные роутеры работают не как точки доступа, а как роутеры
   со своей подсетью, устройства за ними не видны. Спящие телефоны тоже
   могут не отвечать.

Q: Сбоев по проводу нет, а жалобы есть.
A: Значит, проблема в Wi-Fi-части. Ставим такого же агента на устройство
   с Wi-Fi за дальним роутером и сравниваем два отчёта.
