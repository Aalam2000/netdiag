# NetDiag

Мониторинг доступности интернета с проводного сервера.
Работает бесконечно, пока не остановишь вручную.
Пишет лог, потом одной командой строит человекочитаемый отчёт.

## Что делает

Каждые 5 секунд проверяет TCP-подключение к 6 внешним ресурсам:
  - DNS  8.8.8.8:53      (Google DNS)
  - DNS  1.1.1.1:53      (Cloudflare DNS)
  - DNS  9.9.9.9:53      (Quad9 DNS)
  - HTTPS google.com:443
  - HTTPS cloudflare.com:443
  - HTTPS github.com:443

Если все 6 недоступны подряд дольше 30 секунд — фиксируется
"сбой доступа в интернет" с точным временем начала и конца.

Сервер подключён проводом к шлюзу 192.168.0.1. Wi-Fi и TP-Link
в цепи не участвуют — поэтому отчёт показывает состояние
именно канала/провайдера, а не беспроводной части.

## Структура

    /opt/netdiag/
    ├── netdiag.py            # основной скрипт
    ├── Dockerfile            # образ python:3.12-slim
    ├── docker-compose.yml    # запуск контейнера
    ├── data/                 # создаётся автоматически
    │   ├── netdiag.jsonl     # сырой лог (по строке JSON на замер)
    │   ├── netdiag.log       # лог приложения (старт/стоп/GAP)
    │   ├── heartbeat         # метка последнего замера (для детекта простоя)
    │   └── report.txt        # сгенерированный отчёт
    └── script/
        └── netdiag.sh        # управление: start/stop/report/...

## Установка (один раз)

    cd /opt/netdiag
    chmod +x script/netdiag.sh
    sudo systemctl enable docker       # автозапуск Docker после ребута
    docker compose up -d --build       # первый запуск

После этого при включении сервера Docker стартует сам, и контейнер
netdiag поднимается автоматически (restart: unless-stopped).

## Команды

    ./script/netdiag.sh start      # запустить мониторинг (пересобирает образ)
    ./script/netdiag.sh stop       # остановить мониторинг
    ./script/netdiag.sh restart    # перезапустить
    ./script/netdiag.sh status     # статус контейнера + последние строки лога
    ./script/netdiag.sh log        # живой лог контейнера (Ctrl+C для выхода)
    ./script/netdiag.sh raw        # последние 10 сырых замеров из JSONL
    ./script/netdiag.sh report     # построить отчёт по накопленным данным
                                   # (не останавливая мониторинг)
    ./script/netdiag.sh down       # удалить контейнер (данные в data/ остаются)
    ./script/netdiag.sh clean      # удалить контейнер И папку data/

## Типовой сценарий

1. Запустить:
       ./script/netdiag.sh start

2. Убедиться, что пишет (через 30 секунд):
       ./script/netdiag.sh raw
   В каждой строке все 6 целей должны быть "ok": true.

3. Оставить на сутки или двое. Ничего делать не надо.
   Периодически можно смотреть:
       ./script/netdiag.sh status

4. Через сутки-двое — забрать отчёт:
       ./script/netdiag.sh report
   Отчёт печатается в терминал и сохраняется в ./data/report.txt

5. Остановить (когда закончил):
       ./script/netdiag.sh stop

## Простой сервера (отключение питания)

UPS нет. Если питание пропадёт:
  - сервер выключится, netdiag перестанет писать;
  - данные за период простоя потеряны физически;
  - когда сервер включится, Docker поднимет контейнер автоматически;
  - скрипт при старте увидит разрыв в heartbeat и запишет
    в лог "GAP detected", а в отчёт попадёт строка
    "Внимание: в период наблюдения сервер был выключен ...".

Период простоя НЕ считается сбоем доступа в интернет — он явно
выделен в отчёте отдельным блоком.

## Настройка

Всё в начале netdiag.py:

    TARGETS        — список целей (имя, host, port)
    INTERVAL_SEC   — период опроса (по умолчанию 5)
    TCP_TIMEOUT    — таймаут TCP-подключения (по умолчанию 2 сек)
    OUTAGE_MIN_SEC — минимальная длительность серии неудач,
                     чтобы считать это сбоем (по умолчанию 30 сек)

После правки — перезапустить:

    ./script/netdiag.sh restart

## Частые вопросы

Q: Почему TCP, а не ping?
A: В этой сети ICMP заблокирован (шлюз 192.168.0.1 не отвечает
   на ping). TCP-подключение работает и даёт тот же RTT.

Q: Как понять, что проблема НЕ в TP-Link?
A: Сервер подключён проводом к шлюзу, TP-Link'и в цепи
   не участвуют. Если сбои видны в отчёте — они на уровне
   канала/провайдера, а не Wi-Fi.
   Если сбоев НЕТ — значит канал исправен, и вся проблема
   у Wi-Fi-клиентов за TP-Link'ами. Тогда ставим такого же
   агента за TP-Link и сравниваем два отчёта.

Q: Что делать, если сервер перезагрузился?
A: Ничего. Docker с restart: unless-stopped поднимет контейнер
   автоматически. В логе и отчёте появится строка про простой.
